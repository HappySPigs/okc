What is OKC · 한 줄 정의

OKC가 뭔가요?

흩어진 Obsidian 노트 모음(Vault)을 하나의 신뢰할 수 있는 지식 베이스로 “컴파일”하는 시스템입니다. 소스 코드를 빌드하듯이 —

여러 팀의 노트→ AI가 제안→ 코드가 검증→ 사람이 승인→ 하나의 결과물

여러 팀의 노트를 모아 → AI가 정리안을 제안하고 → 코드가 검증하고 → 사람이 승인해야 → 하나의 결과물이 나옵니다.

왜 필요한가 · The problem

Vault를 합치는 순간,
지식보다 판단이 먼저 섞입니다.

각 팀이 로컬 Obsidian을 아무리 잘 써도, 조직 단위로 통합하려는 순간 네 가지 위험이 생깁니다. OKC는 이걸 검색·챗봇 기능이 아니라 컴파일 문제로 다뤄 구조적으로 막습니다.

핵심 아이디어 · The trust model

AI는 제안하고, 코드는 검증하며,
사람만 승인합니다.

OKC에서 AI 출력은 신뢰의 종착점이 아니라 검증의 입력입니다. 소스 텍스트는 명령이 아니라 잠재적으로 적대적인 evidence로 취급합니다.

AI
proposes / 제안

문서 분류(taxonomy), 클러스터별 합성(synthesis), 독립 critic 결과를 제안합니다. 응답은 로컬에서 파싱·검증한 뒤 입력과 해시에 묶습니다.

CODE
verifies / 검증

근거·해시·누락·비평 심각도를 코드로 검증합니다. Major 또는 Critical finding이 남으면 compile 자체가 차단됩니다.

HUMAN
approves / 승인

큐레이터가 명시적으로 승인합니다. 승인은 대상 hash에 묶여, 승인한 내용을 수정하면 기존 승인은 더 이상 유효하지 않습니다.

STEP 1 · AI

가능성을 제안

LLM provider가 분류·합성·critic을 제안. 소스는 검증 대상 evidence.

STEP 2 · CODE

통과 조건을 검사

완전 분할·단일 disposition·evidence 일치·critic 심각도를 코드로 강제.

STEP 3 · HUMAN

대상에 묶인 승인

taxonomy·proposal·critic·revision hash에 연결. Major/Critical은 waive 불가.

STEP 4 · DETERMINISTIC

provider 없이 확정

승인 뒤 compile·verify·explain은 LLM 호출 없이 결정론적으로 동작.

↩︎ Major/Critical finding이 하나라도 남으면 승인 경로가 아니라 재생성(regenerate) 경로로 돌아갑니다.
okc-core · How it merges

okc-core는 어떻게 병합하는가.

비슷한 문서를 곧바로 합치지 않습니다. 유사도는 함께 검토할 후보를 찾는 신호일 뿐, 실제 병합은 모든 입력 조각의 처리 방식·근거·critic·승인이 하나의 계획 안에서 완전히 닫힌 뒤에만 가능합니다.

δ = hash domain · lp(x) = byte 길이를 앞에 붙인 값 · C(x) = key 정렬 + 배열 순서 보존 canonical JSON · 1[조건] = 조건이 참이면 1인 지시 함수 

H_δ(x)          = SHA-256( UTF8(δ) ‖ x )
ID_δ[p1,…,pn] = SHA-256( UTF8(δ) ‖ lp(p1) ‖ … ‖ lp(pn) )
lp(x)          = ULEB128( byte_length(x) ) ‖ x
STAGE 01

움직이는 원본을 내용 기반 ID로 봉인

Markdown을 document·block·metadata로 나누고 정렬한 뒤 내용 기반 hash를 계산합니다. 같은 문장이 여러 Vault에 있어도 occurrence ID가 분리되어 “어느 source의 어느 block인가”를 잃지 않습니다.

봉인된 정규화 텍스트나 corpus 구성이 바뀌면 hash가 바뀌고, 이전 제안과 승인은 stale로 거부됩니다.

δ_block  = "okc:block-content:v3\0"
δ_corpus = "okc:integration-corpus:v3\0"

BlockHash(b) = H_δ_block( UTF8( normalized_text(b) ) )
CorpusHash   = H_δ_corpus( C(documents sorted by DocumentId) )
STAGE 02

두 종류의 점수로 검토 범위만 좁힘

body·frontmatter hash가 모두 같은 exact group을 찾고, Unicode 5-grapheme shingle의 MinHash로 near-duplicate 후보를, embedding cosine으로 semantic 후보를 만듭니다.

기본값: 128 component · 32 bands × 4 rows · threshold 0.85 · 문서당 최대 100 후보. 108/128 = 0.84375는 탈락, 109/128 = 0.8515625부터 후보. 어느 점수도 문서를 자동 삭제하거나 진실을 결정하지 않습니다.

ExactKey(d)  = ( BodyHash(d), FrontmatterHash(d) )
S5(d)        = d의 고유 연속 5-grapheme 집합
sim_MH(a,b)  = (1/128) · Σ 1[ m_j(a) = m_j(b) ]

u(d)         = v(d) / ‖v(d)‖₂
sim_cos(a,b) = u(a) · u(b)
Candidate(a) = Top8 { b : sim_cos(a,b) ≥ 0.55 }
STAGE 03

Taxonomy는 전체 문서의 완전 분할

모든 문서는 정확히 하나의 cluster에만 속해야 합니다. 문서가 빠지거나, 두 cluster에 들어가거나, 빈 cluster나 알 수 없는 ID가 있으면 hard-fail입니다.

Singleton cluster도 synthesis·critic·승인을 모두 거칩니다.

∀ d ∈ Docs :   Σ 1[ d ∈ Ci ] = 1

⋃ Ci = Docs        (누락 없음)
Ci ∩ Cj = ∅  (i ≠ j) (중복 없음)
STAGE 04

모든 조각에 정확히 하나의 처리 + evidence closure

각 target은 Integrated · PreservedVerbatim · OmissionProposed 중 정확히 하나를 가져야 합니다. 합쳤다고 표시한 block은 실제 output evidence에 등장해야 하고, omission에는 사유와 사람 승인이 필요합니다.

Evidence의 세 값은 현재 cluster의 실제 원본 block과 다시 대조됩니다.

T_c = Blocks_c ∪ Metadata_c
set( DispositionTargets_c ) = T_c
IntegratedBlocks_c ⊆ CitedEvidenceBlocks_c

Evidence = ( DocumentId, BlockId, ContentHash )
STAGE 05

Critic과 승인을 하나의 revision hash로 결합

Major/Critical은 waive할 수 없습니다. Minor는 finding ID 전체와 정확히 일치하는 waiver·curator·사유가 필요합니다. 제안·critic·omission·waiver 중 하나라도 바뀌면 revision hash와 plan ID가 달라집니다.

과거 승인 기록만으로 수정된 결과를 통과시킬 수 없는 이유입니다.

MajorFindings ∪ CriticalFindings = ∅
MinorFindingIds = WaivedFindingIds

ClusterRevisionHash = H_δ_revision( C({
    taxonomy_hash, proposal, critic,
    omission_approvals, minor_waivers }) )

IntegrationPlanId = "integration_" ‖ hex( H_δ_plan(…) )
STAGE 06

승인된 계획에서 최종 byte를 다시 생성

Materializer F는 provider 호출 없이 승인 계획에서 cluster당 하나의 note, 원본을 가리키는 legacy stub, plan·provenance·manifest·checksum을 만듭니다. 같은 승인 계획은 같은 byte를 유도합니다.

Core는 staging에서 verify(stage)를 먼저 통과해야만 기존 경로를 덮어쓰지 않는 no-clobber 방식으로 publish합니다. 발행 파일을 몰래 수정하면 read도 VERIFICATION_FAILED로 거부됩니다.

Expected = F( ApprovedPlan )

Verify = ( ActualPaths = ExpectedPaths )
       ∧ ( ∀ p : ActualBytes(p) = ExpectedBytes(p) )
       ∧ ( Manifest, Provenance re-derived from ApprovedPlan )

okc-coreRust · engine

신뢰 규칙을 실행하는 컴파일 엔진

입력을 불변 snapshot으로 봉인하고, 제안을 검증하고, 승인된 계획을 결정론적으로 컴파일합니다. 발행 전에 staging 산출물을 스스로 verify합니다.

okc-hooksRust · daemon

변경을 놓치지 않는 동기화 계층

Obsidian Vault 변경을 감지하고 재시도·재개 가능한 업로드를 수행합니다. 후속 업로드는 같은 논리 소스의 새 revision으로 기록됩니다.

okc-webPython · FastAPI + React

사람이 통제하는 큐레이션 계층

여러 팀의 revision을 모으고, 입력을 freeze하고, taxonomy·cluster review를 진행하고, 승인된 산출물을 발행합니다. 인증·gate·history·restore가 여기 모입니다.

okc-mcpNode · TypeScript

저작과 소비를 잇는 에이전트 인터페이스

사람·AI 에이전트가 로컬 소스 노트를 명시적으로 작성하고, 발행된 revision-pinned 지식을 읽습니다. web 오류 시 조용한 로컬 fallback이 없습니다.

Four-module bridge는 실제 MCP subprocess · Rust CBOR encoder · FastAPI 서비스 · native core binding을 하나의 경로로 연결합니다(LLM은 synthetic provider). 저장소에는 6개 path-scoped CI workflow가 정의되어 있고, 핵심 상태·업로드·저작 로직에는 property-based test를, native binding 경계에는 Rust·Python·Node가 동일 fixture byte에 합의하는 golden test를 적용했습니다.

현재 범위 · Honest boundaries

현재 범위도
명확하게 공개합니다.

  • development-stage 프로젝트이며 okc-web은 single-organization · single-process 해커톤 MVP입니다.
  • 현재 컴파일 산출물은 Markdown 중심입니다. Attachment · Canvas · Base · Pack materialization은 현재 노출 경로 밖입니다.
  • live third-party provider 품질 검증, 전체 native OS service 설치 검증, 성능·배포·package release gate는 후속 과제입니다.
  • MinHash/LSH와 cosine·HNSW를 합치는 통합은 아직 release blocker이며, 현재 organizer가 받는 semantic 후보는 cosine 경로입니다.
  • 해시는 무결성·staleness를 뜻하며 authorship · publisher 신원 · 객관적 진실 · 의미 동등성을 증명하지 않습니다.

이 경계를 숨기지 않는 이유는 간단합니다 — OKC가 파는 가치 자체가 “검증 가능한 주장”이기 때문입니다.

AI 시대의 지식에는 답만큼 “증거”가 필요합니다.

OKC는 그럴듯한 요약을 넘어, 누가 무엇을 제안했고 어떤 근거가 승인됐으며 지금 읽는 byte가 그 승인 결과와 일치하는지 다시 물을 수 있는 조직 지식을 만듭니다.
