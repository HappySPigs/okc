The problem

AI가 합친 지식, 어떻게 믿을 수 있을까요?

일반적인 AI 요약은 읽기 좋지만 중요한 질문이 남습니다.
🔎

어떤 소스가 쓰였나

합성된 문장이 어느 팀·어느 노트에서 왔는지 되짚기 어렵다.

⚖️

모순이 사라지지 않았나

서로 다른 정책·출시일이 매끄러운 한 문장으로 뭉개진다.

✍️

승인 뒤 바뀌지 않았나

사람이 승인한 다음 내용이 수정돼도 승인은 그대로 남는다.

📌

지금 읽는 게 그 결과인가

현재 파일이 바로 그 승인 산출물인지 다시 확인하기 어렵다.

OKC는 이 문제를 검색이나 챗봇 기능이 아니라 컴파일 문제로 다룹니다.
Knowledge loop

한 번 해결한 문제를 다음 작업의 출발점으로

6컷으로 보는 지식 순환
  • Obsidian MCP가 코딩 중 나온 결정·명령·해결법을 개인 Vault에 남깁니다.
  • OKC는 여러 구성원의 Vault를 출처·승인 기록이 남는 부서 공동 아카이브로 만듭니다.
  • 코딩 에이전트가 발행된 부서 지식을 새 구현에서 다시 활용합니다.
  • AI는 taxonomy·synthesis·critic을 제안, 코드는 근거·해시·비평 심각도를 검증, 큐레이터가 승인합니다.
  • 승인된 계획만 provider 없이 결정론적으로 compile · verify · explain 되고, 발행 revision은 고정됩니다.
Why it's hard

Vault를 합치는 순간, 지식보다 판단이 먼저 섞입니다

각 팀이 로컬 Obsidian을 잘 써도, 조직 단위로 통합하려는 순간 네 가지 위험이 생깁니다.
  1. 출처 소실 — 합성된 문장이 어느 팀의 어떤 노트에서 왔는지 알기 어렵습니다.
  2. 모순 은폐 — 서로 다른 출시일·정책이 자연스러운 한 문장으로 뭉개질 수 있습니다.
  3. 승인 드리프트 — 승인 후 제안이 수정돼도 과거 승인이 그대로 남을 수 있습니다.
  4. 버전 혼동 — 최신 발행본과 오래된 로컬 지식이 조용히 섞일 수 있습니다.
팀이 원하는 건 단순한 “노트 병합”이 아니라 검증 가능한 조직 기억입니다.

Core idea

AI는 제안하고, 코드는 검증하며, 사람만 승인합니다

Major/Critical finding이 하나라도 남으면 승인이 아니라 재생성 경로로 돌아갑니다.

① AI는 가능성을 제안

분류·합성·독립 critic을 제안. 소스 텍스트는 명령이 아니라 적대적 evidence로 취급하고, 응답은 로컬 파싱·검증 후 입력·해시에 묶습니다.

② 코드는 통과 조건 검사

모든 문서 1회 처리, block/metadata마다 정확히 하나의 disposition, evidence 해시 일치, Major/Critical 잔존 시 compile 불가.

③ 사람 승인은 대상에 묶임

승인은 taxonomy·proposal·critic·revision hash에 연결. 수정하면 기존 승인 무효, Major/Critical은 waive 불가.

④ 최종 경로는 provider-free

compile·verify·explain은 LLM 호출 없이 실행. 모델·API가 사라져도 내부 일관성을 다시 확인.

okc-core · merge logic

okc-core는 어떻게 병합하는가

유사도는 검토 후보만 좁히고, 완전성·근거·critic·해시 결합 승인이 실제 컴파일 권한을 결정합니다.
  • ① 봉인 — 움직이는 원본을 정규화·정렬해 내용 기반 ID/해시로 고정.
  • ② 후보 축소 — exact group + MinHash/LSH(0.85), 공개 실행은 cosine top-8(0.55). 자동 삭제·진위 판단은 하지 않음.
  • ③ 완전 분할 — taxonomy는 전체 문서의 partition(빠짐·중복·빈 cluster는 hard-fail).
  • ④ 100% disposition — 모든 조각은 Integrated/PreservedVerbatim/Omission 중 하나, evidence closure 필수.
  • ⑤ critic+승인 결합 — blocking 0건 + hash-bound 승인을 하나의 revision hash로.
  • ⑥ byte 재유도 — 승인 계획에서 산출물을 다시 만들어 실제 byte와 비교.
병합 권한 = 완전 분할 + 100% disposition + evidence closure + blocking critic 0건 + hash-bound 승인. 0.85 / 0.55는 자동 병합이 아니라 후보 축소 기준.
Determinism

결정론적 해시로 봉인하고, 무엇이든 바뀌면 stale

δ는 hash domain, lp(x)는 길이 prefix, C(x)는 canonical JSON입니다.
# 내용 기반 identity
H_δ(x)              = SHA-256( UTF8(δ) || x )
BlockHash(b)        = H_δ_block( UTF8(normalized_text(b)) )
CorpusHash          = H_δ_corpus( C(documents sorted by DocumentId) )

# taxonomy는 전체 문서의 완전 분할
∀ d ∈ Docs :  Σ 1[d ∈ Ci] = 1      # union(Ci)=Docs, Ci∩Cj=∅

# 승인을 하나의 revision / plan hash로 결합
ClusterRevisionHash = H( C({ taxonomy, proposal, critic, omissions, waivers }) )
IntegrationPlanId   = "integration_" || hex(H( C({ corpus, policy, taxonomy,
                        approval, cluster_revisions, provider_recordings }) ))
제안·critic·omission·waiver 중 하나라도 바뀌면 revision hash와 plan ID가 달라집니다 — 과거 승인만으로 수정된 결과를 통과시킬 수 없는 이유.
Ecosystem

네 모듈이 하나의 지식 순환을 만듭니다

실선 = 발행 흐름(revision→frozen→plan→vault→pinned), 점선 = LLM proposal-only·MCP 로컬 저작.

okc-hooks Rust

동기화 계층. 변경 감지 + 재개 가능한 업로드. 같은 자격의 후속 업로드는 같은 소스의 새 revision, stale commit은 최신을 못 되돌림.

okc-web FastAPI+React

큐레이션 계층. revision 수집·freeze·review·발행. 인증·review gate·history·restore·read access의 control plane.

okc-core Rust

컴파일 엔진. 불변 snapshot·검증·결정론 compile. 발행 전 스스로 verify, plan에서 파일·provenance·manifest를 재유도해 byte 비교.

okc-mcp Node/TS

에이전트 인터페이스. 로컬 노트 명시 저작 + revision-pinned 지식 읽기. web 오류 시 오래된 로컬로 조용히 전환하지 않음.

okc-mcp

경로를 고민하지 않고, 먼저 확인하고, 안전하게 기록

한 문장으로 세션 기록

사용자가 세션을 선택하고 요청하면 기록. 자동 감시·종료 시 몰래 수집 없음, 매번 user-selected 선언 필요.

경로 선택을 에이전트가 보조

prepare가 관련 노트·heading·폴더 관례·이전 capture 위치를 찾아, 사용자가 경로/생성 여부를 정할 필요 없음.

저장 전 미리보기 + 기존 존중

모든 write는 dry-run 기본. 관련 주제는 기존 section 보강, 무관한 본문·YAML은 보존.

충돌·중복 방지 · 읽기/쓰기 분리

expected SHA-256 확인 + Vault 밖 backup + atomic write + read-back hash. 쓰기는 로컬만, 읽기는 발행 revision 고정.

okc-hooks

설치 후에는 Obsidian에서 평소처럼 저장만

최초 1회 동의

upload 대상·공개 범위 고지 확인 후 standing consent를 줘야 동기화 시작. 언제든 철회, 의심스러우면 차단.

놓친 변경까지 복구

실시간 event + 시작 scan + 주기 reconciliation scan. OS watcher가 놓쳐도 다음 scan이 재확인.

저장 폭주 정리 · 필요한 blob만

연속 save를 debounce, path·SHA-256·size manifest를 negotiate해 없는 blob·미완 구간만 chunk 전송.

중단 지점부터 재개

authoritative resume offset을 따르고, transient failure는 backoff 후 새 event 없이 재시도.

잘못된 대상 방지

state를 Vault path·HTTPS endpoint·token fingerprint에 바인딩. 대상이 바뀌면 명시적으로 중단.

필요할 때만 직접 제어

status·pause·resume·sync-now·history·reload·stop. setup은 재실행 안전, uninstall은 Vault 미변경.

실제 동작 화면

세 부서 샘플을 실제 okc-web·native okc-core 경로로 ingest·freeze·approve·compile·publish·verify한 로컬 실행. 콘텐츠는 deterministic synthetic provider — workflow·계약의 실행 증거이지 live-model 문장 품질 평가가 아닙니다.
Engineering highlights

기술적으로 인상적인 세 장면

🔁

발행 전 자가 검증

승인 계획을 staging에 만든 뒤 스스로 verify, 통과해야 no-replace publish. verify는 manifest를 믿지 않고 embedded plan에서 파일·provenance·checksum을 재유도해 byte 비교 — 직접 수정 시 read도 VERIFICATION_FAILED.

⚖️

모순을 지우지 않는 모델

curator decision에 “승자 선택”이 없음. 타입·SQLite constraint는 approve/regenerate만 허용, omission·minor waiver는 사유 포함 승인에서만. 충돌 주장은 각 evidence와 함께 보존.

📌

revision pinning

Revision A를 읽던 client는 B 발행 후에도 A를 명시 요청해 같은 byte를 읽음. 없는 revision을 현재로 조용히 바꾸지 않으며 history·restore 제공.
