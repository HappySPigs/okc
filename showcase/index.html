03 · WORKING PROOF

개념도가 아니라,
실제 경로를 연결했습니다.

세 부서의 샘플 노트를 실제 okc-web과 native okc-core 경로로 수집·고정·승인·컴파일·발행·검증했습니다.

정확한 증명 범위

deterministic synthetic provider를 사용했습니다. 아래 화면은 워크플로와 계약의 실행 증거이며, live LLM 문장 품질 평가는 아닙니다.

LIVE PATH · 01 / FREEZE

01

판단하기 전에,
입력을 먼저 고정합니다.

Product, Engineering, Research 세 팀의 source revision을 등록하고 하나의 source set으로 freeze했습니다.

  • 기준점 생성검토가 시작된 정확한 입력 집합을 기록합니다.
  • 변경 감지입력이 바뀌면 downstream 승인은 stale이 됩니다.
  • freeze-then-run움직이는 원본 위에 승인을 쌓지 않습니다.
쉽게 말하면

“무엇을 보고 승인했는지”가 나중에도 달라지지 않습니다.

LIVE PATH · 02 / COMPILE

02

승인된 계획만
읽기 전용 Vault가 됩니다.

승인 계획으로 knowledge note, 원본을 보존하는 legacy stub, 검증 proof를 결정론적으로 생성했습니다.

  • 8개 산출 파일knowledge/, legacy/, .okc/로 분리됩니다.
  • publish 전 verifystaging 결과를 먼저 독립 검증합니다.
  • no-clobber기존 결과를 덮어쓰지 않고 새 revision으로 발행합니다.
화면에서 볼 것

verify PASS는 이 결과가 승인 계획과 byte 단위로 일치한다는 뜻입니다.

LIVE PATH · 03 / EXPLAIN

03

결과를 믿으라고 하지 않고,
근거로 돌아가게 합니다.

선택한 compiled note를 세 팀의 source revision, synthesis, 승인 계획과 연결해 보여줍니다.

  • Provenance출력 파일이 어느 source에서 왔는지 설명합니다.
  • Verifyembedded plan에서 기대 byte를 다시 만들어 대조합니다.
  • Fail closed발행 파일이 바뀌면 읽기 자체를 거부합니다.
정직한 의미

Verified는 “내용이 객관적 진실”이라는 뜻이 아니라, 승인 계획과 현재 산출물의 내부 일관성을 뜻합니다.

05 · WHY IT HOLDS

“AI를 잘 썼다”보다
“틀려도 통과하지 못한다”에 집중했습니다.

신뢰는 모델 이름이 아니라, 결과가 만들어지고 읽히는 경계에서 생깁니다.

01

발행 전 스스로 검증

staging에 전체 산출물을 만든 뒤 verify를 먼저 통과해야 no-replace publish가 일어납니다.

compile→verify→publish
검증되지 않은 결과는 발행 경로에 들어갈 수 없습니다.
02

모순을 지우지 않는 모델

큐레이터에게 “승자 선택” 동작이 없습니다. 충돌하는 주장은 각자의 evidence와 함께 보존됩니다.

Claim Aevidence A ≠ Claim Bevidence B
Major/Critical finding은 사유를 붙여서도 무시할 수 없습니다.
03

발행 당시 지식에 고정

새 revision이 나와도 기존 client는 요청한 revision의 같은 byte를 계속 읽을 수 있습니다.

Revision Apinned Revision Blatest
존재하지 않는 버전을 최신본으로 조용히 바꾸지 않습니다.

Provider-dependent proposal과 provider-free 판단 경로를 구조적으로 분리했습니다.

OKC 모듈별 최신 로컬 테스트와 four-module bridge 통과 결과

FOUR-MODULE BRIDGE

실제 MCP subprocess → Rust CBOR encoder → FastAPI → native core binding을 한 경로로 연결했습니다.
