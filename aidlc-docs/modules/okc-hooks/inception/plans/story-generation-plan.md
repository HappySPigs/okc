## 1. 권장 접근 방식 (분석 결과 — 아래 질문으로 언제든 변경 가능)

- **분해 방식**: 하이브리드 **여정(journey) 에픽 + 기능(feature) 하위 스토리**. §3 기능 그룹마다 사용자 가치 중심의 EPIC을 하나씩 두고, 각 FR에 1:1로 매핑되는 기능 하위 스토리로 분해합니다(§4와 FR 목록에 대한 추적성 유지).
- **계층 구조**: 2단계 (에픽 → 하위 스토리). §3 그룹당 에픽 1개 + 횡단 관심사인 **Resilience & PBT** 에픽 1개. 단일 배포 컴포넌트(RESILIENCY-01)이므로 3단계는 불필요합니다.
- **세분화 수준(Granularity)**: 하이브리드 — 기본은 굵게(coarse), FR/PBT 복잡도가 큰 곳만 세밀하게(fine) 분해합니다(업로드 프로토콜 클러스터 FR-05..FR-10/FR-22, 지속 큐/재조정 클러스터 FR-03/04 + PBT-06). 얇은 표면(FR-18 트레이, FR-16 히스토리)은 굵게 유지합니다.
- **PBT 속성** (NFR-08..14 + PBT-06): 별도의 **기술 스토리 트랙**으로 두고 기능 스토리와 상호 연결하여, PBT-01/06/08이 Functional Design 단계까지 추적 가능하도록 합니다.
- **우선순위**: 가볍게만 — 필수(Must-have) MVP 골격(자동 동기화 FR-01/FR-06, have/want FR-07, 재개 업로드 FR-08, 지속 큐 FR-03)만 표시하고, 전체 MoSCoW는 Workflow Planning 단계로 미룹니다(User Stories 규칙 Step 11 준수).
- **후보 에픽**: (E1) 모니터링 & 트리거링 [3.1]; (E2) 업로드 프로토콜 [3.2/§4]; (E3) 오프라인·백프레셔·재시도 [3.3]; (E4) 인증 & 동의 [3.4]; (E5) 히스토리 & 관측성 [3.5]; (E6) 수명주기 & 업데이트 [3.6]; (E7) Resilience & PBT [§5.5/§6].

## 2. 후보 페르소나 (후보 목록 — Q4에서 확정)
- **P1 Vault Owner (주 사용자)** — 설치·설정·동의·편집·모니터링을 모두 하는 단일 사용자. "온보더", "설정 후 방치형 편집자", "문제 해결자", "오프라인 사용자" 모드를 모두 흡수합니다(같은 사람의 다른 여정). 대부분의 스토리가 여기에 귀속됩니다.
- **P2 프라이버시 민감 Vault Owner (관점 변형)** — 같은 사람이지만 동기가 다른 관점. RISK-01 공개(disclosure) 고지, FR-14 동의 조회/철회, FR-16 감사(audit) 스토리를 담당합니다.
- **P3 Headless Operator (조건부)** — GUI 없는 Linux 데몬 운영자. **헤드리스 범위가 확정될 때만 포함**(Q5). 데스크톱 세션이 없으면 FR-18 트레이, FR-19 데스크톱 알림, FR-21 로그인 자동시작, FR-13 Secret Service가 매핑되지 않습니다.
- **제외됨**: OKC 서비스 관리자(서버는 범위 밖 §2.2 → 페르소나가 아니라 DEP-01..07 외부 계약으로 표현); 멀티 디바이스 사용자(별도 인물이 아니라 Q2로 해결되는 토폴로지 문제).

## 3. 후보 여정 (후보 목록 — 최종 집합은 답변에 따라 확정)
1. 최초 실행 온보딩: 설치 → 볼트 선택 → 토큰 붙여넣기 → 상시 동의(standing consent) 부여 (+ RISK-01 공개 고지 확인). *(최초 실행 시 단일 인스턴스 잠금, OS 권한 부여를 엣지 케이스로 흡수)*
2. 정상 상태에서 단일 편집의 자동 동기화 (감시 → 디바운스 → 매니페스트 → have/want → 전송 → 커밋).
3. 초기/대용량 볼트의 재개 가능(resumable) 업로드 + 진행률. *("첫 대용량 업로드" + "초기 전체 동기화" 병합)*
4. 오프라인 → 재연결: 지속 큐 배출(drain) + 합치기(coalesce).
5. 시작 시 + 주기적 재조정(reconciliation): 중단 중 놓친 변경 복구.
6. 업로드 실패 → 백오프 → N회 연속 실패 알림 (인증 실패 + 토큰 재입력 포함).
7. SafetyLimit 사전검사(preflight) 거부 (최초 실행 **및** 런타임 중 용량 증가).
8. 동의 조회/철회 (서버가 생기기 전까지는 전진 방향(forward-only)만).
9. 자동 업데이트 + 업데이트 후 헬스 체크 + 자동 롤백.
10. 업로드 히스토리 조회/쿼리 (경량).
11. **볼트 사용 불가 / 빈 볼트 안전 가드** — *요구사항에 없던 항목; 완전성 검토자(critic)가 발견.* 볼트 루트가 언마운트/삭제/이동되어 FR-02 매니페스트가 파일 0개로 보이면 diff가 "전부 삭제"로 판단해 서버에 파괴적인 빈 커밋(FR-09)을 보낼 수 있는 상황을 방지합니다. Q13 참조.

## 4. 분석에서 새로 드러난 항목 (현재 요구사항에 없음)
아래 질문에 답하시면 현재 FR 집합을 넘어서는 **파생(derived) 스토리/요구사항**이 소수 생길 수 있습니다. 이는 승인된 요구사항을 다시 여는 것이 아니라 예상된 스토리 수준의 구체화입니다. 주요 항목: **빈 볼트 안전 가드**(Q13), **실행 상태 일시정지/재개 + "지금 동기화"**(Q11), **동의 철회 시 로컬 동작 + 새 트레이 상태**(Q6), **제거/폐기 시 로컬 평문 산출물 + 토큰 정리**(Q13), **토큰 회전/재입력**(여정 6에 흡수). 디스크 고갈 처리, FR-22 스냅샷 방식 선택, OS 알림 권한 부여는 별도로 당기지 않는 한 **Functional Design** 단계로 넘깁니다.
