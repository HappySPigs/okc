# Session capture usage and recovery

A writable local MCP connection advertises the session-capture workflow at initialization but does not run it. Both tools default userSelected to false and reject an omitted/false declaration before scanning or writing. The host sets true only for the session/content explicitly selected by the user in this request; this declaration is not independent authentication of human intent. Ask the coding agent to record the session in the relevant notes, or select the capture_session prompt. The host reads okc://guide/session-capture, extracts topic queries and calls prepare_session_capture; it then reads local candidates, selects paths/sections and previews/applies apply_session_capture. No user path or create/update choice is required.

Preparation returns a sessionId; reuse it with stable item IDs. A new note needs title and expectedHash=null. Existing notes need the whole-file hash from local reads and optionally the full section path returned by preparation. Several items targeting one note are written together with one backup. Replaying the same successfully applied payload is a no-op even if the original read hash is stale, because unchanged bytes are not rewritten. Changed content always requires a fresh hash.

Preview returns per-item content snippets (with truncation flags), paths, reasons and proposed hashes. Only dryRun=false applies a change. An explicit user selection/request to save grants the ordinary local-write scope only for that selected content and the retries needed to finish it, so the guide proceeds after inspecting the preview without asking the user to select destinations. Compiler review/publication authority is unaffected.

Persistence uses balanced okc-capture comments. They let preparation locate the previous item after reconnect or an external file rename. Keep marker pairs intact; duplicates, nested markers, unclosed code fences and changed destinations are rejected. Restore damaged content using the existing external backups after inspection.

The batch is preflighted but is not a cross-file transaction. partial/failed is an MCP error carrying per-file receipts; inspect applied/verified flags, failure and remainingPaths, then prepare again and retry with the same identities and fresh hashes. Existing successful blocks are reused. The per-process capture gate and existing per-note locks/hash checks do not claim a multi-process transaction against arbitrary external Vault editors.

Source selection is always local for preparation and application. Published web knowledge remains separately available through existing tools. The host model owns semantic interpretation; lexical candidates are evidence, not a semantic equivalence score. No session is recorded automatically on startup, task progress/completion, compaction, shutdown or new messages. After a capture completes, later updates require another user selection. This implementation does not install transcript collectors or session-end hooks.
